01 · Background

Why do we need synchronization?

What happens if two threads change the same data at the same time?

Processes or threads may run concurrently and access shared data. If their operations overlap in an unsafe order, the final result can be wrong. This is called a race condition.

Example: A shared bank balance is 100. Two threads each add 10. The correct final balance is 120, but both may read 100 and write 110.

02 · The Critical-Section Problem

Protect shared data

A critical section is the part of a program that accesses shared data or a shared resource. Only one thread should execute a particular critical section at a time when mutual exclusion is required.

A correct solution should satisfy mutual exclusion (only one inside), progress (a decision is not postponed unnecessarily), and bounded waiting (no thread waits indefinitely while others repeatedly enter).

03 · Hardware Support

Atomic operations

Processors provide atomic instructions, such as test-and-set or compare-and-swap. An atomic operation completes as one indivisible action, helping software implement synchronization safely.

Simply checking whether a lock is free and then setting it is unsafe if another thread can interrupt between those steps. An atomic test-and-set combines the check and update.

Try atomic test-and-set

The first thread obtains the lock. Another thread cannot obtain it until it is released.

04 · Mutex Locks

One lock, one owner

A mutex lock protects a critical section. A thread acquires the mutex before accessing shared data and releases it afterward. Other threads must wait while the mutex is held.

05 · Semaphores

Control access to available resources

A semaphore is a synchronization variable changed through atomic wait and signal operations. A binary semaphore has values 0 or 1; a counting semaphore can represent several available resources.

Example: A lab has three printers. The counting semaphore starts at 3. Each successful wait reserves one printer; each signal returns one.

06 · Monitors

Shared data + controlled operations

A monitor groups shared data and the operations that access it, while ensuring mutual exclusion for monitor operations. Condition variables allow threads to wait until a condition becomes true and be notified when it changes.

07 · Classic Problems of Synchronization

Three problems to recognize

Producer–ConsumerProducers add items to a bounded buffer; consumers remove them. Coordinate full and empty conditions.
Readers–WritersMultiple readers may read concurrently, but writing requires exclusive access to shared data.
Dining PhilosophersSeveral philosophers share forks. Poor resource-acquisition rules can cause deadlock or starvation.
Interactive bounded buffer (capacity 3)

A producer adds an item; a consumer removes one. The producer cannot add when full, and the consumer cannot remove when empty.

Exam Practice · 3 Short Questions

Question 1What is a race condition? Explain the critical-section problem and the three requirements of a correct solution.
A race condition happens when concurrent operations on shared data produce a result that depends on their execution order. A critical section is the code accessing shared resources. A correct solution needs mutual exclusion, progress, and bounded waiting.
Question 2Compare mutex locks, counting semaphores, and monitors with one example for each.
A mutex gives one thread exclusive access to a critical section, such as updating a bank balance. A counting semaphore controls access to multiple resources, such as three printers. A monitor organizes shared data and synchronized operations, for example a bounded buffer with wait/notify conditions.
Question 3Explain the Producer–Consumer problem. What happens when the buffer is full or empty?
A producer places items into a shared bounded buffer, and a consumer removes them. When full, a producer must wait for space; when empty, a consumer must wait for an item. Synchronization prevents unsafe concurrent buffer updates and coordinates these waits.
